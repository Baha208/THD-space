# THD Space

THD Studio (interior design, Cairo) client presentations: one mobile-first web app per
client, used to walk them through floor plans and 3D renders, working documents and reports on
a phone or tablet. Each presentation is a static PWA; there is no build step, framework or backend.
Every presentation has exactly three top-level tabs, in this order: **3D Views** (the floor tabs,
floor plans, rooms and render gallery), **Working Documents** and **Reports** (PDF lists).

Alongside them, `hub/` is a separate installable app for the internal team ("THD Space"): a list
of all projects, plus Library and News sections that are **placeholders only** (see Hub below).
Presentations never link to or mention the hub; the hub only links into them.

## project.json

Authored fields are written by hand; generated fields are overwritten by the script.

```jsonc
{
  "schemaVersion": 2,                     // 2 = this layout; the generator refuses anything else
  "slug": "jane-doe-villa",              // = folder name under projects/
  "client": "Jane Doe",                   // required (generator errors if empty)
  "title": "Jane Doe’s Villa",            // required; shown in header, loader, <title>, manifest name
  "sourceDir": "3d-views",                // the 3D Views folder, in the project folder
  "floors": [                             // order = floor tab order (inside 3D Views)
    {
      "id": "ground",                     // unique in the project; used in DOM ids. --init makes
                                          // it from the full folder name: "ground-floor-level"
      "label": "Ground Floor",            // used in the gallery header ("Reception · Ground Floor")
      "tabLabel": "Ground",               // optional short floor tab text (falls back to label); keep
                                          // it one word so the floor tabs fit on one line at phone width
      "dir": "ground floor level",        // exact folder name on disk, case included
      "planDir": "floor plan",            // optional, default "floor plan"
      "plan": "…/Ground floor plan.webp", // GENERATED
      "rooms": [                          // order = button order
        { "id": "reception", "label": "Reception", "dir": "reception",   // id unique within its floor
          "images": ["…/reception1.webp", "…"],   // images GENERATED
          "medium": ["…/medium/reception1.webp", "…"] }   // GENERATED: copy per image, or null;
                                                           // absent when the room has no copies
      ]
    }
  ],
  "documents": {                          // PDFs shown in the "Working Documents" tab
    "dir": "Working-documents",           // in the project folder, next to sourceDir
    "files": [                            // MERGED, not overwritten (see below); newest date first
      { "file": "Working-documents/2026-08-23-Cabinets details.pdf",
        "label": "2026-08-23 Cabinets details", // authored once generated: never overwritten
        "date": "2026-08-23" },           // GENERATED from a "YYYY-MM-DD-" filename, else absent
      { "file": "Working-documents/GF-electrical_layout.pdf", "label": "GF Electrical Layout" }
    ]
  },
  "reports": {                            // PDFs shown in the "Reports" tab; same rules as documents
    "dir": "Reports",
    "files": [
      { "file": "Reports/2026-09-30-Tiles schedule.pdf", "label": "2026-09-30 Tiles schedule", "date": "2026-09-30" }
    ]
  }
}
```

Paths in project.json are relative to the project folder and stored raw (spaces, `&`);
app.js URL-encodes each segment. Room/floor ids exist only here — nothing else to keep in sync.

**schemaVersion 1** (before October 2026) kept the PDFs inside the renders folder
(`3d views & working documents/Working documents/`), with no reports. The generator refuses such a
file with instructions and writes nothing; convert it by hand: rename the folders on disk to the
layout above, set `"schemaVersion": 2` and `"sourceDir": "3d-views"`, change the start of every
`plan`/`images`/`medium` path to `3d-views/`, set `"documents": { "dir": "Working-documents",
"files": [] }` and add `"reports": { "dir": "Reports", "files": [] }`, then run the generator
(it relists the PDFs; re-edit their labels if needed). The app itself ignores schemaVersion.

## generate-manifest.js

```
node engine/generate-manifest.js projects/<slug>              # fill project.json + write manifest.json
node engine/generate-manifest.js projects/<slug> --dry-run    # print result, write nothing
node engine/generate-manifest.js projects/<slug> --init       # new project: project.json + index.html + sw.js
```

It reads only schemaVersion 2 (see above). An older project.json is an error with instructions.

- Re-run it whenever renders are added, removed or renamed. The app never guesses filenames.
  When renders change, run the medium-copy script instead: it makes the missing copies and then runs
  the generator itself (see below), so one command covers both.
- Images: every .webp/.avif/.jpg/.png in the room folder, natural sort (2 before 10). No renaming.
  Subfolders are not scanned, so a room's `medium/` copies never count as renders.
- Medium copies (needs sharp: once, from THD SPACE/, `npm install --prefix tools`):
  ```
  node tools/make-medium-renders.js projects/<slug>
  ```
  One command: it runs the generator with --dry-run to get the current render list, writes any
  missing copies, then runs `node engine/generate-manifest.js projects/<slug>` for real (writing
  project.json and manifest.json). It fails, writing nothing, while client/title are empty.
- `medium`: for each image, "<room>/medium/<same name>.webp" if that file exists, else null. The
  copies come from tools/make-medium-renders.js (long edge 1500 px, WebP q80; originals of 1600 px or
  less get none). It never touches originals, skips copies that exist unless the original is newer,
  and warns instead of overwriting when two originals (a.jpg + a.webp) would share one copy.
- Folder names must match the disk **exactly** — Windows ignores case, production hosting doesn't.
  The script errors on a case mismatch or missing folder and writes nothing.
- New folders not yet in project.json are appended as rooms with a warning; fix their label/order.
  Any folder in the project folder other than `3d-views/`, `Working-documents/` and `Reports/`
  (e.g. a leftover old-layout folder) is warned about and ignored.
- `--init` needs `3d-views/`, guesses labels and orders floors alphabetically — always review
  before publishing. It writes index.html and sw.js from engine/templates/ (never overwriting
  existing ones), creates empty `Working-documents/` and `Reports/` if they're missing (git ignores
  empty folders until they hold a PDF), and skips manifest.json until client/title are filled in.
  Outside `--init`, an empty client or title is an error.
- Duplicate ids are an error: floor ids across the project, room ids within a floor.
- PDF lists, `documents` (`Working-documents/`) and `reports` (`Reports/`), follow the same rules:
  - Only `.pdf` files in that folder count (others are skipped with a warning). A missing or empty
    folder is fine (the tab shows its empty state); a name that differs only in case is an error.
  - New PDFs get a label from the filename. A name starting with a real date `YYYY-MM-DD-` gives
    `"date"`, and the label is the date, one space, then the rest of the name as typed (`-`/`_`
    turned into spaces, case kept): "2026-09-30-Tiles schedule.pdf" → label "2026-09-30 Tiles
    schedule", date "2026-09-30". (Before engine v12 the label left the date out; labels made then
    were updated by hand, since the generator never rewrites a label.) Any other name, or an
    impossible date (2026-02-30), uses the older rule: "GF-electrical_layout.pdf" → "GF Electrical
    Layout" (words capitalised, all-caps words kept).
  - Existing labels are never overwritten, so edit them freely. `date` is regenerated from the
    filename on every run (rename the file to change it).
  - Order: dated entries newest first, then undated ones in their existing order. Re-sorted on
    every run, so a hand-made order of dated entries doesn't stick.
  - A listed PDF that's gone from disk is warned about but **kept** — delete its entry by hand if
    that was intended.
- manifest.json colors come from `--ink` in engine/tokens.css; icons point into engine/images/icons/.
  "maskable" entries use icon-maskable-192/512.png (the mark scaled to a 76% circle, inside
  Android's 80% safe circle, on ink); every other entry is the edge-to-edge icon-<size>.png. The
  maskable files are committed assets, made once from icon-512.png; to remake them (e.g. new logo): `npm install --prefix tools` once,
  then `node tools/make-maskable-icons.js` (from THD SPACE/). They are shared, not per project.

## New client

Run every command from the `THD SPACE/` folder. Needs Node 18+.

1. Create `projects/<slug>/3d-views/` (exactly that name) with one folder per floor, each holding a
   `floor plan/` folder (one image) and one folder per room (its renders). PDFs go in
   `projects/<slug>/Working-documents/` and `projects/<slug>/Reports/`, next to `3d-views/`; both are
   optional (step 2 creates them empty). Name PDFs `YYYY-MM-DD-<label>.pdf` (e.g.
   `2026-09-30-Tiles schedule.pdf`) to show a date and sort newest first.
   Renders and floor plans can be `.webp`, `.jpg`/`.jpeg`, `.png` or `.avif` (any letter case;
   formats can be mixed in one room). Step 5 makes a `.webp` medium copy from any of them. The
   originals are shown as they are when zoomed, so prefer `.webp` or `.jpg`: `.png` is large, and
   `.avif` doesn't display on iPhones older than iOS 16. Two originals with the same name in one room
   (`a.jpg` + `a.webp`) would share one copy, so step 5 skips the second with a warning — rename it.
2. `node engine/generate-manifest.js projects/<slug> --init` — writes project.json, index.html, sw.js,
   and creates `Working-documents/` and `Reports/` if they're missing.
3. In project.json, fill in `client` and `title`; check floor order, ids and labels.
4. Only once per computer (skip if `tools/node_modules/` already exists): `npm install --prefix tools`
5. `node tools/make-medium-renders.js projects/<slug>` — makes the medium copies of the renders, then
   runs `node engine/generate-manifest.js projects/<slug>` itself, which adds the `medium` lists to
   project.json and writes manifest.json. Nothing else to run.
   (If sharp can't be installed: run `node engine/generate-manifest.js projects/<slug>` instead. It
   writes manifest.json; the gallery then opens the full-size originals, which just load slower.)
6. If the project has PDFs: `node tools/optimize-pdfs.js projects/<slug>` — makes them smaller for
   phones (see "PDF optimizer"), keeps the originals in `_originals/`, then runs the generator itself.
   Needs qpdf once per computer: `winget install --id QPDF.QPDF -e` (and sharp, step 4).
7. `node tools/generate-projects-index.js` — adds the project to the hub's Projects list
   (projects-index.json) and refreshes hub/manifest.json's colours. Plain Node, no install needed.
8. Serve the root and open `/projects/<slug>/` (or tap it in the hub at `/hub/`).

Later changes:

| Change | Run |
|---|---|
| Renders added, removed or renamed | step 5 |
| Only labels or order changed | `node engine/generate-manifest.js projects/<slug>` (step 5 also works) |
| PDF added to `Working-documents/` or `Reports/`, or replaced by a new export (same name) | step 6 (optimizes it and runs the generator) |
| PDF deleted on purpose | delete its entry in project.json and in pdf-optimized.json, then the generator |
| Project added or removed, or its folder/client/title changed | step 7 |
| `tools/pdf-optimize.config.json` changed (settingsVersion bumped) | step 6 again: it re-derives from `_originals/` |

`node tools/optimize-pdfs.js projects/<slug> --check` lists PDFs not yet optimized (exit code 1 if any).

## PDF optimizer (tools/optimize-pdfs.js)

PDFs from AutoCAD carry 3D renders pasted onto the sheets at 150–400 dpi, far more than our viewer
can ever show: pdf-view.js draws each page into one canvas capped at 8 MP, so on an A0 sheet it
never shows more than about 74 dpi, at any zoom (A1 ~104, A3 ~210). The optimizer brings such images
down to what the viewer can show and changes nothing else.

```
node tools/optimize-pdfs.js projects/<slug>              # optimize what isn't done yet, then run the generator
node tools/optimize-pdfs.js projects/<slug> --check      # list PDFs not yet optimized; exit 1 if any
node tools/optimize-pdfs.js projects/<slug> --preview    # optimized copies + report + before/after images in a
                                                         # temp folder (or --out=DIR); the project is untouched
node tools/optimize-pdfs.js projects/<slug> --dry-run    # report only
node tools/optimize-pdfs.js projects/<slug> --force      # re-derive everything from _originals/
```
(`--only=TEXT` limits it to matching paths; `--headroom=N` overrides the config, only with --preview/--dry-run.)

- **Engine: qpdf + sharp, surgical.** qpdf (found on PATH, else in `C:\Program Files\qpdf*\bin`,
  else PDF24's bundled copy) dumps the PDF; the script reads every page's content to find where each
  image is drawn and how large, and re-encodes only JPEG renders that are well above the target
  (target = `headroom` × the viewer's maximum for that page size; resampled only when more than
  `resampleAbove` × over it), with their soft masks resized to match. qpdf writes those streams back
  and repacks the file losslessly (object streams, maximum Flate). Vector linework, text, fonts,
  links, bookmarks, layers, annotations and transparency are never touched or rasterized.
- **Headroom 1.0** (settingsVersion 2, October 2026): chosen after comparing 1.5 and 1.0 side by side
  in our viewer (Chrome and WebKit), which showed no visible difference; 1.0 roughly halves the big
  file. If MAX_CANVAS_PIXELS in engine/pdf-view.js is ever raised, raise `viewerMaxCanvasPixels`
  and/or `headroom` in the config, bump `settingsVersion`, and run `--force` (from _originals/).
- **Left alone on purpose** (both found in the first preview, where the gates caught visible damage):
  images under `minResamplePixels` (1 MP) or with a side under 256 px, because AutoCAD builds some
  pictures (the title-block logo) from many thin image strips that seam when resampled one by one;
  and images whose soft mask is more than `maxMaskTransparentPercent` (1%) fully transparent, because
  those are translucent outlines and fills (line art stored as a picture), not renders. Also left
  alone: non-JPEG images (kept lossless), CMYK and unusual colour spaces, JPEGs with their own colour
  profile, and images also used outside page content.
- **Gates — all must pass or the original is kept** (recorded as "kept-original" so it isn't
  retried): same pages, sizes and rotation; every object reachable from the catalog unchanged once
  decoded, apart from the resampled images (so text, fonts, links, bookmarks and layers are
  identical); each resampled image ≥ `minImagePsnrDb` against an ideal downscale of its original (a
  fine texture steps its JPEG quality up from 80 to 85/90/95 to get there); sample pages rendered
  before/after with Ghostscript (when found; PDF24's copy works), images interpolated as PDF.js
  does: whole page at the viewer's 1x ≥ `minRender1xPsnrDb`, worst of 16 tiles at the maximum zoom
  ≥ `minRenderZoomTilePsnrDb`; and at least `minSavingPercent` smaller. Don't loosen these to make a
  file pass — find out what changed (--preview writes the before/after images).
- **Originals and the ledger:** before a PDF is replaced, the original is copied to
  `_originals/<same path>` (checked byte for byte); the new file is staged next to the target and
  renamed over it (same name, so labels and dates don't change). Output is always derived from the
  original, never from an optimized file. `pdf-optimized.json` (tracked) records original and output
  sha256/size and the settings version, so reruns skip finished files and a teammate who cloned the
  repo (no _originals) doesn't re-compress. A PDF replaced by a new export is treated as a new
  original (a different earlier backup is kept as `<name>.replaced-<time>.pdf`).
- **_originals/ exists only on the computer that ran the optimizer** (gitignored, never published).
  Keep the source PDFs somewhere else as well (the studio's project files).
- **Biggest saving for future files:** lower the raster image resolution in AutoCAD's PDF export
  options (DWG to PDF / plot settings, about 150 dpi). The renders are then small to begin with.
- generate-manifest.js reads the ledger and tools/pdf-optimize.config.json: a listed PDF over
  `warnUnoptimizedMB` (15) that isn't optimized (not in the ledger, or changed since) gets a warning
  with the command to run; an optimized PDF still over `noteOptimizedMB` (25) gets a soft note
  ("export with a lower raster resolution"). It ignores `_originals/`.

Villa results (October 2026, headroom 1.0): Internal elevations 34.3 → 15.8 MB (40 renders
resampled), Cabinets details 5.6 → 3.1 MB, Working plans 4.6 → 4.1 MB (lossless repack only),
Tiles schedule kept (1.5% saving, under the 5% minimum).

## Hub (hub/)

The team's own installable app, "THD Space". Separate from the presentations in every way: own
manifest, own service worker and caches, own icons. It shares only engine/tokens.css (colours and
fonts) with them. Nothing in engine/ or projects/ links or refers to it — keep it that way, so a
client presentation never exposes internal pages.

- Bottom tab bar (the app's top-level sections; distinct from the floor tabs inside a presentation):
  **Projects** (default), **Library**, **News**. The open tab is in the URL hash (`#projects`,
  `#library`, `#news`) with replaceState, so reloads keep it and switching tabs adds no history
  entries; any other hash, including the old `#reports`, opens Projects. Text only, no logo in the
  chrome (same rule as the presentations: the install icon is the branding).
- Page zoom is fully locked, as in the presentations: the viewport meta has maximum-scale=1 and
  user-scalable=no, `html` has touch-action: pan-x pan-y (no double-tap zoom), and hub.js blocks
  iOS's gesturestart/change/end and two-finger touchmove (iOS ignores user-scalable=no). The hub
  has nothing that needs zooming, so unlike the presentation gallery there is no scoped zoom.
- Zoned colours, using the shared zone tokens from engine/tokens.css (see Conventions → Zones):
  header and bottom tab bar `--chrome-bg`; header title `--chrome-text`; the "THD SPACE" kicker
  and inactive tabs `--chrome-text-muted`; content area `--content-bg`, full height on every tab
  (placeholders too); each panel opens with a schedule head ("Project index" + count;
  "Library" / "News" + 00) and project rows are schedule rows, exactly as a presentation's room
  rows (see Conventions → Design language) — future Library/News items should reuse them; active
  tab `--chrome-text` with the accent bar on its top edge, as the floor tabs. `html`/`body` are
  `--chrome-bg` too, so iOS overscroll matches the chrome.
- Status bar: installed on iOS the hub uses `apple-mobile-web-app-status-bar-style`
  black-translucent (with viewport-fit=cover), so the ink header runs up under the clock and
  battery; the header pads its top by `env(safe-area-inset-top)` and the tab bar its bottom by
  `env(safe-area-inset-bottom)`, so the kicker/title and tabs never sit under the status bar or
  the home indicator.
- **Tab bar height (engine v13 / hub-v7).** In an installed hub on iOS the bar could be taller right
  after launch than after the first scroll, by exactly the top safe-area inset. Cause: a WebKit
  bug with black-translucent in home-screen apps: at launch the page is laid out shorter than the screen
  by the status-bar height until the first scroll, so a bar at `bottom: 0` floats that much too
  high with html's ink showing under it (reported by others; see the hub.js comment). It was not
  the remembered-inset probe (that value only ever grows, so it can't explain a bar that gets
  thinner). Fix: (1) the bar's bottom padding is iOS's own constant `env(safe-area-inset-bottom)`
  only, never measured or remembered; (2) in an iOS home-screen app only (`navigator.standalone`),
  hub.js compares innerHeight with the screen height for the orientation; a shortfall of 1–80 px
  is that bug, handed to the CSS as `--viewport-gap`, and the bar moves down by exactly that
  much (rechecked on scroll/resize, so it goes back to 0 once WebKit corrects itself). Temporary
  diagnostic: `?debug=1`, or
  five quick taps on the "THD Space" kicker (the installed app has no address bar; it stays on, in
  localStorage, until five more taps), shows a small yellow box with env() insets, innerHeight,
  visualViewport.height, screen size, standalone, the gap applied and the bar's position. Remove
  it (hub.js "DIAGNOSTIC", the end of hub/styles.css) once the fix is confirmed on a device.
- Safe areas after a round trip to a project: in the installed hub on iOS, tapping a project opens
  it in the in-app Safari sheet over the still-running hub (no reload), and after Done the header
  was seen under the notch again, although a fresh open was fine. Only the reported
  `env(safe-area-inset-*)` values can change without a reload, so the likely cause is WebKit
  leaving them at 0 after the sheet (which owns the status bar) is dismissed, until the next
  viewport change; iOS may fire no event on that return. Fix (hub.js "SAFE AREAS" + the top of
  hub/styles.css): a hidden probe measures the insets on load and on resize/orientationchange/
  pageshow/focus/visibilitychange, remembers the largest per orientation for the session, and the
  CSS pads the header with max(live env(), remembered) via --sa-top (the top only; since hub-v7 the
  bottom is never remembered, see Tab bar height). It needs no event on the return, never adds the
  two, and landscape keeps its own values. If it still happens, the next thing to try is
  re-applying the viewport meta on return to make WebKit recompute the insets.
- **Opening animation** (hub only; a presentation's loader does real loading work and stays as it
  is): on ink, three thin accent rings pulse outward (staggered), the "THD" mark
  (hub/splash-mark.png: the same extracted mark as the icons, top line only, accent) fades and
  scales in over the first third, then "SPACE" (accent, small, wide tracking) fades in below;
  ~1.5s, then a 0.3s fade reveals Projects. Flat colours only (no blur, no gradients). It always
  plays to completion once it starts: taps and keys during it do nothing (there is no skip).
  Deliberate behaviour — don't "fix" it into always playing:
  - **Cold start only**, tracked in **sessionStorage** (key `thd-hub-intro`), deliberately not
    localStorage: it plays when the app is freshly launched (a new session), never when it is
    resumed from the background during the day, reloaded, or returned to from a project in the
    same session. An inline script in index.html's <head> decides before the first paint (adds
    `html.intro-playing`), so a non-cold start never even flashes it.
  - Reduced motion: no rings or scaling; the mark and word show still for ~0.9s.
  - The `html` flag class is `intro-playing`, not `intro`: `.intro` is the overlay's own
    class (display: none by default), and sharing the name hid the whole page.
- Projects: reads `../projects-index.json` and shows one row per project (title, client), each a
  plain link to `../projects/<slug>/`. That is a normal navigation out of the hub's scope, so the
  project's own service worker takes over there. In the installed hub, iOS/Android show the project
  in an in-app browser view with a Done/close control back to the hub. The hub's scope is only
  hub/ on purpose: a site-wide scope would open projects inside the hub window, where iOS has no
  back gesture and presentations have no link back. A missing or broken index shows an inline
  error with its path.
- **Library and News are placeholders pending further direction**: a static "Library — coming
  soon" / "News — coming soon" screen each. There is deliberately no data file, schema or loading
  code for them. Don't treat them as features or invent a structure without a brief. (Library
  replaced a "Reports" placeholder in October 2026, once reports moved into each presentation's own
  Reports tab; the name is neutral on purpose and not tied to any planned content.)
- generate-projects-index.js scans every folder in projects/ and lists it when project.json parses,
  its "slug" equals the folder name, client and title are filled in, it has floors, and the folder
  has index.html; anything else is skipped with a warning saying why. Entries `{ slug, client,
  title }`, sorted by title. Rerun it whenever a project is added, removed or renamed, or its
  client/title changes (the hub never scans folders itself — a static host can't list them).
  It also sets hub/manifest.json's "theme_color" and "background_color" from --ink in
  engine/tokens.css (the same rule generate-manifest.js applies to each project's manifest),
  leaving every other field there as authored. So after changing --ink, rerun it too.
- Service worker (hub/sw.js, scope hub/): precaches the hub files (splash-mark.png included, so the
  intro works offline), its icons, engine/tokens.css,
  the two fonts it uses and projects-index.json, so the tabs and the project list work offline
  after one visit. Hub files and the index are network-first (a new index shows up when online);
  tokens/fonts stale-while-revalidate. Its caches are named `thd-hub:<scope>:<VERSION>` and never
  touch a project's. **Bump `VERSION` in hub/sw.js whenever a hub file changes** (independent of
  engine/sw.js's VERSION).
- hub/manifest.json: name, scope, display and icons are written by hand; its two colours are
  generated from engine/tokens.css by generate-projects-index.js — don't edit them by hand.
- **Icons are a placeholder treatment, not a final design decision**: the THD mark from
  engine/images/icons/icon-512.png recoloured to ink, on a full-bleed accent-yellow (#FEFB28)
  square, so it can't be confused with a client presentation's ink icon on the same phone. The
  "any" icons keep the mark's size/position from the project icons; the maskable ones fit it in
  a 76% circle, inside the 80% safe circle. Remake with `node tools/make-hub-icons.js` (after `npm install --prefix
  tools` once), or replace the files in hub/icons/ when real artwork exists.

## Runtime behavior

- Tabs: three top-level tabs in one row, always all three, in this order: **3D Views**, **Working
  Documents** and **Reports**. All three fit on one line down to 320 px: on phones each tab starts
  at its label's width and shares the spare room (`flex: 1 1 auto`), with tab-label letter-spacing
  0.08em (0.14em again from 640 px); never let them wrap. The open one is kept in the URL hash, `#3d-views`, `#working-documents` or
  `#reports`, with replaceState (passing the existing history.state through, so history.js's
  overlay marker is never cleared): a reload keeps it, switching adds no history entries, and a
  missing or unknown hash opens 3D Views. Inside 3D Views a second row holds the floor tabs (one
  per floor, `tabLabel || label`, no numbers; it scrolls sideways if many floors don't fit); the
  floor always starts on the first one and isn't in the hash. Both rows sit in one sticky ink
  block (`.chrome-bars`, see Safe areas); the floor row is hidden on the other two tabs. Working
  Documents and Reports each list their PDFs as schedule rows under a head with the count (the
  label, which for a dated file starts with the date, e.g. "2026-08-23 Cabinets details": the date
  is set in figures on the first line and the name below, the text itself unchanged; a "PDF" tag;
  an arrow), newest first, or "No working documents yet" / "No reports yet" on one ruled line.
- 3D Views, per floor: the sheet label ("First Floor" · "Sheet 02 / 03", the floor's position and
  the number of floors) on an ink rule, the floor plan printed on the sheet below it, then the
  "Spaces" schedule (count on the right): one row per room with its index, name, view count
  (number of renders) and an arrow; the whole row opens the gallery. The room last opened on that
  floor keeps the marker (`is-current`), so after closing the gallery the client sees where they
  were.
- Loader waits only for project.json, fonts and the **first** floor plan. Other plans load in the
  background; a room's renders load when the room is opened (gallery prefetches next/previous).
- Failures are never silent: a missing project.json / first plan stays on the loader and lists each
  path; a missing later plan or render shows an inline error with the path, and logs to the console.
- Zoom (zoom.js, used by the gallery and the PDF viewer) is a CSS transform on one element —
  the page viewport never zooms. Pinch / double-tap (touch), wheel / double-click (mouse), max 4x.
  Zoomed in, a drag pans (clamped so the content keeps covering the screen). Gallery: the render
  zooms; swipe-to-navigate only at 1x; zoom resets on every image change, close, and rotation.
- Progressive renders (gallery.js): a render opens as its medium copy; once that is on screen the
  original is fetched and decoded in the background. Zooming past 1x swaps in the original (with the
  image box locked, so nothing moves), back at 1x the medium copy returns. A missing medium copy falls
  back to the original silently; the original failing while zoomed keeps the medium copy. Neighbours
  are prefetched as medium copies.
- Back button: opening the gallery or the PDF viewer pushes a history entry (history.js), and
  Android back / iOS swipe-back pops it and closes the overlay instead of leaving the app. Closing any
  other way (×, Escape, backdrop) removes the entry with history.back(); that popstate is recognised
  and ignored, so back never needs pressing twice and close never runs twice. A reload with an
  overlay open neutralises the stale entry.
- PDF viewer (both lists use the same one): tapping a row fetches the PDF (so failures show inline
  under that row with the path: "Could not open document: <path> (HTTP 404)" or "(no connection, and
  not saved on this device yet)"), then shows it in a full-screen in-app overlay (app.js "viewer":
  dark backdrop, close button, Escape, focus back to the row, back button). The whole file is
  downloaded before PDF.js can draw page 1, so while it comes in the viewer shows "Downloading 4.2 /
  36.0 MB" (the total only when the server sends Content-Length); a large PDF on a slow connection
  takes as long as the transfer (see Known open items). Not an
  `<iframe>` (iOS shows only page 1 of an embedded PDF and can't zoom it) and not a new tab (a
  target="_blank" in an iOS home-screen app opens in the app's webview with no way back).
  pdf-view.js hands the fetched bytes to PDF.js (imported on first use) and stacks one `<canvas>`
  per page in a scroll container. Every page gets a sized placeholder; pages are drawn only within
  one screen of view and freed further away. Zoom applies to the whole page stack: at 1x the stack
  scrolls natively (plain mouse wheel scrolls; Ctrl+wheel / trackpad pinch zooms), zoomed in a drag
  pans, and zooming out turns the pan into scroll position. When a zoom settles, pages in view are
  redrawn at the zoomed resolution, capped at 8 MP per canvas (iOS canvas memory).
- PDF.js's worker starts from a same-origin blob that imports engine/pdfjs/pdf.worker.min.js, so the
  worker belongs to the page and its requests go through the project's service worker (a worker
  loaded straight from engine/ would be outside its scope and fail offline). If a worker can't
  start, PDF.js runs the same file on the main thread.
- Service worker (scope = project folder): precaches the engine shell, project files and floor plans
  on install; renders and PDFs are cache-first as viewed (PDFs from both lists in one cache named
  "documents", never precached), so anything seen once works offline. PDF.js has its own cache named
  after `PDFJS_VERSION` (survives VERSION bumps); pdf.min.js + pdf.worker.min.js are precached when
  project.json lists any PDF in documents or reports, fonts/wasm are cached as used. PDF navigations are routed before the app-shell rule, and
  only full 200 responses are cached. **Bump `VERSION` in engine/sw.js whenever engine files change.**
  Updating PDF.js: replace engine/pdfjs/ from the pdfjs-dist `legacy/` build (keeps older iOS
  working), rename the two .mjs files to .js (not every host serves .mjs as JavaScript), and change
  `PDFJS_VERSION` in sw.js.

## Conventions

- Brand tokens live only in engine/tokens.css `:root`: ink #231F20, ink-soft #3E393B, gray #616161,
  mist #E9ECEB, accent #FEFB28 (+ white, error). engine/styles.css and hub/styles.css both
  @import it and define no colours of their own.
- Zones (engine/tokens.css, built only from the colours above; used by the presentations and the
  hub alike): `--chrome-bg` (ink) for header and tab bars, `--chrome-text` (white) for titles and
  the active tab, `--chrome-text-muted` (white mixed 55% into ink) for chrome labels and inactive
  tabs, `--chrome-divider` (hairline inside the chrome), `--content-bg` (mist) for the area
  between the chrome, which reads as a drawing sheet with **no boxes on it** (the white cards were
  removed in engine v13 / hub-v7): `--content-text` (ink) and `--content-text-muted` (gray) for
  text on it, `--rule` (ink at 18%) between rows, `--rule-strong` (ink) under sheet and schedule
  heads, `--row-press` (ink 7% into mist) for a pressed or hovered row, and `--marker-bg` (ink) /
  `--marker-text` (accent) for the index cell of a pressed or current row. In a presentation: the
  header and both tab rows (top-level tabs, and the floor tabs below a `--chrome-divider` hairline)
  are chrome; the panels and footer are content; the active tab in each row keeps the accent bar
  on its bottom edge. The gallery, the PDF viewer and the loader are not zoned (dark overlays /
  white loader, unchanged).
  Change a zone in tokens.css, never with local colours in a stylesheet.
- **Design language (engine v13 / hub-v7, October 2026): the drawing sheet.** The content area is
  styled like the studio's own drawings, so the app reads as THD's and not as a generic list:
  - The floor plan is printed on the page (`mix-blend-mode: multiply`: its white paper becomes
    the mist, lines and colours stay), under a sheet label in BankGothic caps ("Ground Floor",
    "Sheet 01 / 03") on an ink rule, like a title-block strip. Its container is mist too, because
    the fading panel is its own compositing group and multiply needs a backdrop inside it.
  - Lists are schedules, not cards: a head (name + count, ink rule), then ruled rows with a
    32 px square index cell, the name in BankGothic caps, quiet meta in Inter (view count, client,
    the date) and a thin square-capped arrow. Square corners and 1 px rules only. Rooms, PDFs and
    the hub's projects use the same row, so the two apps teach one pattern.
  - Yellow appears only for what is active or selected: the tab bars' accent bar, and the index
    cell of a pressed row or of the room last opened (ink square, yellow figures, 14.8:1). Yellow is
    never put on mist (1.1:1, invisible).
  - Rules applied, with the numbers measured: text contrast ≥ 4.5:1 (muted on ink 5.8, gray on mist
    5.2, gray on a pressed row 4.6, ink on mist 13.7; the old faded tab index was 2.7 and its fade
    was removed); touch targets ≥ 44 pt (rows 56–64, top tabs 56+, floor tabs 44, hub tabs 56+,
    whole rows tappable); every control has a pressed state (`:active`; app.js and hub.js add an
    empty touchstart listener because iOS Safari applies `:active` only then), a hover state on
    hover devices only, and a 2 px focus outline in the zone's text colour (`:focus-visible`);
    text never below 11 px; spacing on a 4/8 px scale; motion under 200 ms (`--motion-fast`
    120 ms for feedback, `--motion` 180 ms for the tab bar and panel fade) and off with
    prefers-reduced-motion. Exceptions, on purpose: the hub's opening animation (a brand moment,
    documented above) and zoom.js's 250 ms zoom transition (zoom internals, untouched).
  - Thumb reach: the villa's tabs stay at the top (the tab/hash behaviour is fixed), but every
    repeated action is a full-width row in the reachable middle of the screen; the hub's sections
    are in the bottom bar.
- Status bar and safe areas (presentations and hub alike): index.html uses
  `apple-mobile-web-app-status-bar-style` black-translucent and `viewport-fit=cover` (in
  engine/templates/index.html too, so new projects get it), so installed on iOS the ink chrome runs
  up under the clock with no white strip. engine/styles.css ("SAFE AREAS") defines --sa-top/right/
  bottom/left from env(safe-area-inset-*) and pads everything that could end up under the status
  bar, home indicator or landscape side notch: header (top + sides), both tab rows (sides), content
  and footer (sides, footer bottom), gallery close button/stage/arrows/caption, PDF viewer
  close button/pages/caption. The two tab rows share one sticky block (`.chrome-bars`) that sticks
  at `top: var(--sa-top)` (not padded, so there's no empty band above it under the header); the
  floor row needs no offset of its own, it just makes the block taller when shown. A fixed ink
  `body::before` strip the height of the status bar sits behind it so content scrolling up never
  shows under the clock.
  The loader (white, full screen) covers that strip while loading. Every inset is 0 on screens
  without a notch, so desktop/Android layout is pixel-identical to before. Any new element placed
  at a screen edge must use the --sa-* values the same way. No raw colors elsewhere; theme-color meta is set
  by app.js / hub.js from `--ink`, manifest colors by scripts (generate-manifest.js for each project,
  generate-projects-index.js for hub/manifest.json). After changing a colour token, rerun both.
- Fonts: BankGothic for display (uppercase, tracked), Inter for body, declared once in
  engine/tokens.css (font URLs are relative to it, so they resolve to engine/fonts/ from any
  importer). All self-hosted — no CDNs, so the apps work offline.
- Studio-wide copy ("interior design" kicker, "THD Studio — Cairo, Egypt" footer) lives in the
  STUDIO constant in engine/app.js.
- No THD logo inside the app: the loader and header are text only (kicker + title; centred title).
  The mark is seen on the home-screen icon (favicon, apple-touch-icon, manifest icons), which is
  where branding belongs; don't add it back to the loader/header.
- Plain browser JS (IIFEs, no modules, no dependencies). The one exception is PDF.js, vendored in
  engine/pdfjs/ and loaded with `import()` only when a PDF is opened. The Node script needs only
  Node 18+.

## Known open items

- Viewport disables page pinch-zoom (`user-scalable=no`); only gallery images and PDF pages (in the
  PDF viewer, through the same zoom.js) zoom.
- iOS ignores `user-scalable=no`; zoom.js blocks its `gesturestart` to compensate.
- Large PDFs open only after the whole file has downloaded (pdf-view.js takes the bytes in one
  piece; no range/streaming loading), so time-to-first-page equals transfer time; locally every
  villa PDF opens in 1–2 s, so the engine itself is fine. The PDF optimizer (above) keeps files
  small; the remaining option is range-based loading in pdf-view.js (a bigger change; the service
  worker can't cache 206 responses).
- PDF optimizer limits: inline images and images inside patterns or annotation appearances are
  never resampled; unembedded fonts stay unembedded (Tiles schedule's Arial Bold: the viewer
  substitutes a font, as before); linework-heavy PDFs (Working plans: 66% vectors) only get the
  lossless repack. Not yet tried on PDFs from Illustrator/InDesign/Excel with large images (the gates
  apply to any PDF, but the rules were tuned on AutoCAD output).
- PDF pages have no text layer: text in a PDF can't be selected or searched, and links in it
  don't work. Very large sheets zoomed to 4x hit the 8 MP canvas cap and soften slightly.
- Renders: originals ~2500–3300 px (~480 KB avg); medium copies ~180 KB avg. No thumbnails yet.
- Serving the whole root also publishes `THD studio brand identity/`, `tools/` (with its
  node_modules) and every `projects/<slug>/_originals/` (the full-size PDFs) — exclude them when
  deploying. Deploy engine/, projects/ (without _originals/), hub/ and projects-index.json. Deploying
  from a git checkout excludes all three automatically (they're gitignored or not needed). The hub is then reachable by anyone who knows /hub/ (it has no login); it
  only lists project titles and clients, but keep that in mind before adding internal content.
